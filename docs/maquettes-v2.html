Périmètre

Ce que contient cette étape, et ce qui attend

Inclus dans l'étape 1

  • Connexion Discord, Google, ou e-mail + mot de passe (avec « mot de passe oublié »).
  • Pseudo unique choisi à la première connexion, et couleur préférée retenue.
  • Mode invité inchangé : un pseudo libre, pas de stats.
  • Profil : parties jouées, Korol, durak, série récente, historique.
  • Classement des joueurs connectés.
  • Reprise des parties après une mise à jour du site : plus de partie coupée par un déploiement.
  • Le minuteur démarre après l'annonce de l'atout.

Étapes suivantes

  • Étape 2 · Bots : compléter une table ou jouer seul, deux niveaux. Les parties avec bots ne comptent pas au classement.
  • Étape 3 · Matchmaking public : file d'attente par nombre de joueurs, réservée aux comptes connectés (modération plus simple).
  • Retrait définitif : un joueur connecté retiré par l'hôte ne peut plus revenir dans ce salon (possible dès qu'il y a des comptes).
Architecture

Supabase garde ce qui doit durer, le serveur arbitre toujours

Le serveur de jeu actuel ne change pas de rôle : il distribue, cache les mains et tient le minuteur. Supabase (offre Cloud gratuite) gère les comptes et la base de données. Le navigateur ne peut jamais écrire un résultat lui-même.

navigateur (React)                  serveur de jeu (Node, VPS)              Supabase Cloud
 ├─ connexion Discord / Google ───────────────────────────────────────────► Auth
 │   / e-mail ◄───────────── jeton de session (JWT) ◄──────────────────────┘
 ├─ socket.io + jeton ───────────► vérifie le jeton, sait qui joue
 │                                 arbitre la partie (moteur actuel)
 │                                 fin de partie ── écrit le résultat ────► Postgres
 │                                 (clé service, jamais côté client)        games, game_players
 └─ profil, classement ──────────────────────── lecture seule ────────────► vues player_stats
                                   arrêt du serveur ── sauvegarde ─► disque du VPS ─► rechargé au démarrage

Pourquoi pas Supabase Realtime à la place de Socket.IO

  • Les mains doivent rester cachées : un canal Realtime diffuse la même chose à tous, il faudrait ré-arbitrer chaque coup dans des fonctions serveur.
  • Le minuteur et le jeu automatique d'un joueur absent demandent un serveur qui tourne en continu.
  • Le moteur actuel (51 tests) reste tel quel : moins de risques.

Reprise après mise à jour

  • À l'arrêt, le serveur enregistre tous les salons et parties sur le disque du VPS (un volume Docker), puis les recharge au démarrage.
  • Les joueurs se reconnectent tout seuls : la partie reprend là où elle était, minuteur relancé.
  • Pas besoin d'écrire chaque coup dans Supabase : plus rapide et gratuit.

De ton côté

Ce que tu devras préparer (je te guiderai pas à pas)

Aucune clé secrète ne doit passer dans le chat : elles iront directement dans les secrets GitHub et sur le VPS.

  1. Créer le projet Supabase sur supabase.com (région Europe), puis me donner l'URL du projet et la clé publique anon.
  2. Créer une application Discord (portail développeurs Discord) et coller son identifiant et son secret dans Supabase → Authentication → Providers.
  3. Créer un identifiant OAuth Google (Google Cloud Console), même principe.
  4. Ajouter la clé service Supabase dans les secrets GitHub : le déploiement la transmettra au serveur de jeu sur le VPS.
